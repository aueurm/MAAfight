**下一步最值得验证的是关卡配置身份、兼容能力说明和分层评估。** 本轮离线实验表明，现有 10 关 benchmark 覆盖的原始机制类型有限；直接继续扩大候选搜索，无法解决输入含义不清或验收样本偏窄的问题。下面保留低成本方向，也保留完整模拟、众包评测等高成本设想，供选择而非立即实施。

**离线实验：现有样本覆盖哪些原始机制。**

输入是 `src/data/stage_index.json`、对应的本地固定 level 快照和 `benchmark/stages/basic.json`。以规范化后的 `levelId` 去重，得到 2,344 份正式索引引用的 level，文件全部存在。本轮直接检查 JSON 字段，不运行 adapter，也没有重复统计此前的可解析 / 拒绝总数。

定义 26 个可由字段直接识别的标签。每个标签只计“这一份 level 是否出现”，不按敌人数、路线数或 stage 别名重复加权。路径排除 `null` 和 `E_NUM / 2`；地形只统计地图矩阵实际引用的 tile。隐藏分组、难度 rune、随机分组仍按原始存在性计数，**没有推断它们在默认难度是否启用**。因此标签数衡量样本涉及的输入类型，既不是测试覆盖率，也不是机制实现率或通关率。

3,226 条正式 stage 记录对应 2,344 份 level。其中 882 份被两个 stage ID 共用，44 份还对应两个不同的显示 code。仅使用文件路径或显示编号作为实验身份，会混淆不同入口或配置；也可能让训练集和验收集表面分离、实际引用同一地图。

有三个直接影响取舍的结果：

1. 随机分组出现在 107 份正式样本中，低部署上限出现在 126 份中，当前 benchmark 都没有覆盖。它们比“再加一张普通早期主线图”更能提供新的边界信息。
2. 传送类路径有 602 份、预置 token 有 1,452 份，benchmark 各只有一份。已有一个样本不足以说明不同事件组合都被正确解释，但也不能把这些计数一概视为缺陷。
3. 最小样本选择会偏爱一关包含多种机制的关卡。它适合压缩输入类型清单，却不适合单独定位根因；后续还需挑选隔离单个机制的样本。

**可选方向。** 成本是相对工程量判断，不是交付承诺。表中的最小验证可以先证伪方向，避免一次实现完整系统。
