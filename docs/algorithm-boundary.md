# MAAfight 算法边界与路线说明

## 背景

MAAfight 当前不是 AI / LLM 生成脚本工具，而是基于 PRTS.Map 真实关卡数据的规则化 MAA copilot JSON 草稿生成器。

主链路集中在：

- `src/battle/BattleAnalyzer.ts`
- `src/battle/ScriptGenerator.ts`
- `src/core/pipeline.ts`

当前流程是：

```text
真实关卡数据
  -> 地图适配
  -> 战斗分析
  -> 干员选择
  -> 部署动作生成
  -> MAA copilot JSON 导出
```

MAAfight 的价值在于把 PRTS.Map 的地图、路线、波次、敌人属性等数据转成一份可供人工检查和 MAA 执行的 copilot 草稿。它不负责控制模拟器，不做图像识别，也不替代 MAA 的执行引擎。

因此，算法演进应该优先提升规则规划质量，而不是把项目扩展成完整的明日方舟战斗模拟器。

## 为什么不做完整模拟

完整战斗模拟理论上可行，但不适合作为 MAAfight 的近期目标。

原因不是“完全做不到”，而是它会把项目性质从“规则脚本生成器”变成“明日方舟战斗引擎复刻器”。这会显著扩大数据范围、规则数量、测试难度和维护成本，也会让 MAAfight 偏离当前边界。

完整模拟至少需要维护这些系统：

- 干员基础属性
- 精英化、等级、信赖、潜能成长
- 技能倍率、持续时间、初始技力、回转
- 天赋、模组、召唤物
- 攻击范围、攻击间隔、前摇
- 阻挡数、索敌规则、治疗规则
- 敌人连续路径移动
- 飞行、隐匿、高防、高抗、Boss 等特殊机制
- 费用、击杀回费、先锋技能回费、关卡特殊规则

这些内容不只是数据表问题。真实战斗中还有大量联动规则和特例。例如技能改变攻击范围，天赋影响费用或阻挡，召唤物占用部署位，敌人特殊能力改变阻挡和索敌结果。要让模拟结果可信，就必须持续追踪游戏版本变化并补齐大量边界规则。

更重要的是，即使模拟器认为某份脚本可以通关，MAA 实际执行也可能失败。原因包括：

- 图像识别延迟
- 点击延迟
- 模拟器帧率波动
- 倍速差异
- 自动技能时机偏差
- 任务队列执行和暂停时机误差

因此，完整模拟不应进入 MAAfight 主链路，也不应作为“脚本可通关”的证明。

## 推荐分层路线

MAAfight 的算法能力可以分为三层。

### 第一层：轻量规划

这一层是近期目标。

它不模拟完整战斗，只用已有关卡数据做规则化规划：

- `pressureWindows`：按时间段统计敌人压力，包括敌人数、总 HP、总攻击、是否有飞行 / 精英 / Boss。
- 任务队列：用 `early_dp`、`lane_block`、`lane_hold`、`anti_air`、`arts_damage`、`healing`、`boss_kill` 等任务替代固定职业顺序。
- 粗费用：估算干员部署费用和自然回费，避免连续生成明显费用不足的部署动作。
- 点位评分：根据路线、蓝门、隘口、远程覆盖、治疗覆盖等规则选择更合理的部署点。

这一层仍然是规则脚本生成，不承诺战斗结果，只提升生成草稿的合理性。

### 第二层：半模拟

这一层可以选择性实现，但只能作为评分辅助。

它可以估算：

- 敌人沿路线推进的大致压力
- 阻挡点压力
- 远程位覆盖路线数量
- 医疗位覆盖核心阻挡位
- Boss 或精英波次附近的部署风险

半模拟的输出只能用于：

- 点位评分
- 部署顺序排序
- warning
- `metadata`
- GUI 调试展示

半模拟结果不能用于承诺通关，也不能替代人工检查。

### 第三层：完整模拟

这一层不是 MAAfight 近期目标。

完整模拟会尝试覆盖：

- 干员攻击
- 技能轴
- 天赋
- 模组
- 召唤物
- 敌人特殊机制
- 真实费用和击杀回费
- 连续移动、阻挡、索敌、治疗

如果未来确实要做，应该作为独立研究项目或独立模块评估，而不是直接塞进 MAAfight 主链路。

## 近期应该做什么

近期应该把 MAAfight 继续做成更稳定、更可解释的规则规划器。

优先事项：

1. 在 `BattleAnalyzer` 中增加 `pressureWindows`。

   按固定时间窗口聚合敌人压力，记录敌人数、总 HP、总 ATK、飞行 / 精英 / Boss 标记。

2. 在 `BattleAnalyzer` 中增加 `recommendedTasks`。

   从压力窗口、路线类型、平均 DEF、Boss / 精英情况推导任务队列，而不是只输出职业数量。

3. 在 `ScriptGenerator` 中优先消费任务队列。

   让干员选择从“职业优先”逐步转向“任务和功能优先”。已有六星功能画像和玩家干员库仍然可以复用。

4. 增加粗费用时间线。

   估算自然回费和部署费用，在连续部署明显费用不足时插入更合理的等待时间。

5. 增加部署点评分。

   地面单位优先靠近敌人路径、蓝门和隘口。远程单位优先覆盖更多路径。医疗优先覆盖已规划的核心阻挡位。

6. 将新分析信息写入 `metadata`。

   GUI 可以展示 `pressureWindows`、`recommendedTasks`、费用估算、部署点评分和 warning，帮助测试者反馈问题。

## 不应该做什么

近期不应该做：

- 不实现完整战斗模拟器。
- 不把模拟结果当作通关证明。
- 不在主链路中引入复杂技能轴。
- 不维护全量干员属性、天赋、模组和召唤物规则。
- 不复刻 MAA 已经负责的执行层能力。
- 不因为半模拟评分较高就自动声明脚本稳定可用。
- 不破坏当前能生成合法 MAA copilot JSON 的能力。

MAAfight 输出的脚本应始终被视为 copilot 草稿，需要人工检查，并以 MAA 实际执行结果为准。

## 对主链路的约束

主链路应保持当前边界：

```text
PRTS.Map 数据
  -> MapData
  -> TacticalAnalysis
  -> BattleScript
  -> MAA copilot JSON
```

约束如下：

- `BattleAnalyzer` 可以增加分析字段，但不得依赖完整战斗模拟结果。
- `ScriptGenerator` 可以根据任务队列、费用估算和点位评分调整部署顺序。
- `ScriptGenerator` 必须保留 fallback：当新字段不存在或评分失败时，回退到旧的 `requirements` / `deploymentOrder` 逻辑。
- 玩家干员库不足时，继续沿用 `operatorGaps` 行为。
- `metadata` 可以包含调试信息，但不应改变 MAA copilot JSON 的执行语义。
- `pipeline` 应继续负责串联加载、分析、生成、验证、导出，不承载模拟器职责。
- 导出的 JSON 必须继续兼容 MAA copilot v3 格式。

## 后续可扩展方向

后续可以按风险从低到高逐步扩展。

1. 任务化规划增强

   将职业数量需求转成任务队列，并为每个任务记录来源、优先级和推荐时间。

2. 压力窗口调试

   在 GUI 中展示压力窗口，帮助用户看到脚本为什么选择防空、法伤、治疗或 Boss 处理任务。

3. 粗费用校验

   输出部署费用估算和可部署时间，提示明显过早的部署动作。

4. 点位评分解释

   在 `metadata.deploymentReasons` 中写入点位选择原因，例如“靠近隘口”“覆盖 3 条路线”“覆盖核心阻挡位”。

5. 半模拟 warning

   对疑似风险输出 warning，例如“核心阻挡位治疗覆盖不足”“Boss 窗口前缺少高伤任务”“飞行路线缺少防空任务”。

6. 独立模拟研究

   如果未来要探索完整模拟，应单独建立边界和数据源，不应让它成为 MAAfight 生成脚本的必要前置。

最终定位应保持清晰：

> MAAfight 是基于 PRTS.Map 的规则化 MAA copilot 草稿生成器，而不是明日方舟战斗模拟器。
